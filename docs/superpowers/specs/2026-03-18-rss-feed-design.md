# RSS Feed — Design Spec
**Date:** 2026-03-18
**Status:** Approved

## Overview

Add a daily-generated RSS feed to the a2events static site. The feed is generated by a new standalone Python script (`generate_rss.py`) that reads the existing `docs/events.json` and writes static RSS 2.0 XML files to `docs/`. GitHub Actions commits and serves them via GitHub Pages alongside the existing site.

---

## Goals

- Publish a machine-readable RSS feed of upcoming local events
- Support filtering by category (one feed per category + one unified feed)
- Fit naturally into the existing scrape → merge → commit pipeline
- Require no new runtime dependencies

## Non-Goals

- Per-tag feeds
- Atom format (RSS 2.0 covers all major readers)
- Server-side or dynamic feed generation
- User subscription management

---

## Architecture

```
merge.py → docs/events.json
                │
                ▼
        generate_rss.py
                │
                ├── docs/feed.xml                (all events)
                ├── docs/feed-arts-culture.xml   (arts_culture category)
                └── docs/feed-community.xml      (community category)
                │
                ▼
        GitHub Actions git commit step
        (adds feed files alongside events.json via glob)
                │
                ▼
        GitHub Pages (public URLs)
```

Note: The actual `scrape.yml` workflow has a two-job structure (`scrape` → `deploy`). The diagram above shows the logical data flow within the `scrape` job only.

`generate_rss.py` is a standalone script. It:
1. Reads `docs/events.json` (exits non-zero with error log if missing or malformed)
2. Filters events to a **30-day rolling window** from today (matching the scraper window)
3. Sorts events chronologically (by `date`; `time` is treated as an opaque display string and not used for sorting due to inconsistent formats across scrapers)
4. Writes one XML file per feed (all + per active category)

---

## Feed Configuration

At launch, three feeds are generated — one unified and two per-category. Only categories with scrapers in production get feeds. Future categories are added by extending the `FEEDS` config dict in `generate_rss.py`.

| Feed | File | Filter |
|------|------|--------|
| All Events | `docs/feed.xml` | none |
| Arts & Culture | `docs/feed-arts-culture.xml` | `category == "arts_culture"` |
| Community | `docs/feed-community.xml` | `category == "community"` |

Other categories present in `events.json` (e.g. `city_ann_arbor`, `university_of_michigan`, etc.) are intentionally excluded from per-category feeds at launch — they are planned future sources with no active scrapers yet.

**Adding a future category feed:** Add an entry to the `FEEDS` dict in `generate_rss.py`. No other files need to change (the `git add` step uses a glob — see GitHub Actions section).

## RSS 2.0 Format

Generated using `lxml.etree` (already in `requirements.txt` for scraper use). lxml is chosen over stdlib `xml.etree.ElementTree` to support `etree.CDATA()`, which wraps HTML description content in proper `<![CDATA[...]]>` sections for RSS readers. No new dependencies are added.

Output begins with the standard XML declaration:
```xml
<?xml version='1.0' encoding='UTF-8'?>
```
(`ElementTree.write(..., xml_declaration=True, encoding='utf-8', pretty_print=True)` produces this automatically — lxml normalizes the encoding attribute to uppercase.)

### Channel-level fields (per feed)

```xml
<channel>
  <title>A2 Events — All</title>
  <link>https://example.github.io/a2events/</link>
  <description>Upcoming events in Ann Arbor, Ypsilanti, and Washtenaw County</description>
  <lastBuildDate>Wed, 18 Mar 2026 06:05:00 +0000</lastBuildDate>
  <ttl>1440</ttl>
  ...items...
</channel>
```

- `<link>` — set from a `SITE_URL` constant at the top of `generate_rss.py`. The developer must set this to the actual GitHub Pages URL (e.g. `https://username.github.io/a2events/`) before deployment. It is not read from the environment.
- `<lastBuildDate>` — current UTC time at script execution, formatted as RFC 822.
- `<ttl>1440</ttl>` — 24 hours, matching the scrape cadence.

### Item-level fields (per event)

```xml
<item>
  <title>The War on Drugs @ The Ark</title>
  <link>https://theark.org/events/...</link>
  <description><![CDATA[
    <p><strong>March 15, 2026 — 8:00 PM</strong><br>
    The Ark · 316 S Main St, Ann Arbor, MI<br><br>
    An evening with The War on Drugs...</p>
  ]]></description>
  <pubDate>Sun, 15 Mar 2026 00:00:00 +0000</pubDate>
  <guid isPermaLink="false">ark-2026-03-15-the-war-on-drugs</guid>
  <category>arts_culture</category>
</item>
```

**Field mapping:**

| RSS field | Source | Notes |
|-----------|--------|-------|
| `<title>` | `"{title} @ {venue}"` | If `venue` is empty/null, use just `title` (omit ` @ `) |
| `<link>` | `event.url` | Always present (required by schema) |
| `<description>` | CDATA HTML block | See below |
| `<pubDate>` | `event.date` at midnight UTC, RFC 822 | See note on pubDate below |
| `<guid>` | `event.id` | `isPermaLink="false"` |
| `<category>` | `event.category` | |

**`<pubDate>` note:** This field is set to midnight UTC of the event date (not the scrape time). This is a deliberate deviation from the RSS spec's intent (which is "when the item was published"). The rationale: RSS readers display items chronologically, and using the event date causes items to sort by when the event occurs rather than when the scraper ran. This makes the feed behave like a date-sorted event listing rather than a news feed. Subscribers should be aware that items for future dates will appear out-of-order relative to newer scrape runs.

**`<description>` CDATA block structure:**

```html
<p><strong>{date_formatted} — {time}</strong><br>
{venue} · {address}</p>
<p>{description}</p>
```

Rules:
- `date_formatted`: event date formatted as "March 15, 2026"
- `time`: displayed as-is from `event.time` (no normalization — formats vary by scraper)
- If `venue` is empty/null: omit venue entirely (no ` · ` separator)
- If `address` is empty/null: omit address (and ` · ` separator) from the venue line
- If `venue` and `address` are both empty: omit the venue/address line entirely
- If `description` is empty/null or whitespace: omit the `<p>{description}</p>` block entirely

**`possible_duplicate` events:** Included in feeds without modification. The frontend also shows these events; excluding them from feeds would create inconsistency.

Items sorted chronologically by `event.date` (ascending). Within the same date, original order from `events.json` is preserved.

## GitHub Actions Integration

One new step added to `.github/workflows/scrape.yml` after `python merge.py`:

```yaml
- run: python generate_rss.py
```

The existing `git add` line is updated to use a glob for feed files, so future category feeds require no workflow changes:

```yaml
# Before:
git add docs/events.json data/raw/

# After:
git add docs/events.json docs/feed*.xml data/raw/
```

The `git diff --cached --quiet || git commit` guard and all other parts of the commit step remain unchanged.

## Testing

`tests/test_generate_rss.py` — unit tests using pytest, no network calls. Tests call internal functions of `generate_rss.py` directly (not the CLI entry point).

| Test | Assertion |
|------|-----------|
| Item count | Feed contains correct number of items for given input |
| Category filtering | Arts/community feeds exclude events from other categories |
| Date windowing | Events outside the 30-day window are excluded |
| Field mapping | `<title>`, `<link>`, `<guid>`, `<pubDate>`, `<category>` map correctly |
| Title fallback | Event with empty venue produces title without `@ ` suffix |
| Description fallbacks | Empty venue/address/description each handled correctly |
| Possible duplicate inclusion | Events with `possible_duplicate: true` are included |
| Ordering | Items are sorted by date ascending |
| Valid XML | Output is parseable by `xml.etree.ElementTree` |
| XML declaration | Output begins with `<?xml version` declaration |
| Error on missing JSON | Script exits non-zero if `docs/events.json` is missing |
| Error on malformed JSON | Script exits non-zero if `docs/events.json` is not valid JSON |

---

## Constraints & Notes

- `SITE_URL` constant in `generate_rss.py` must be set to the actual GitHub Pages URL before deployment.
- `generate_rss.py` is idempotent — safe to run multiple times; overwrites previous output.
- The `FEEDS` dict in `generate_rss.py` drives which files are generated. Adding a new category feed only requires updating that dict.
